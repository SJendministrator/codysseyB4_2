# [Analysis] 로그 패턴 분석을 통한 스케줄링 알고리즘 추론 (보너스)

|---|---|

| 결론 | **비선점(Non-preemptive) Priority 스케줄링**으로 추론 (표본 1회, 아래 한계 참고) |

## 1. 로그 관찰 개요

정상 모드로 부팅하면 앱이 작업 스케줄러를 만들고 작업 3개(`Thread-A`, `Thread-B`, `Thread-C`)를 등록한 뒤 실행한다. 각 작업은 진행률을 20% 단위로 로그에 남기므로, **타임스탬프와 진행률**을 보면 어떤 작업이 언제 CPU를 받았는지, 중간에 다른 작업이 끼어드는지 알 수 있다.

## 3. 패턴 분석

| 후보 | 로그에서 보여야 할 모습 | 이번 로그 | 판정 |
|---|---|---|---|
| **Round-Robin** | 작업이 끝나기 전에 일정 간격(타임 퀀텀)으로 다른 작업과 번갈아 실행 (A 20% → B 20% → C 20% → A 40% …) | 각 작업이 20% → 100%까지 **한 번도 끊기지 않음** | ✗ |
| **FCFS** | 먼저 들어온(등록된) 순서대로 끝까지 실행 → A, B, C | 비선점인 점은 맞지만 **실행 순서가 B, C, A**로 등록 순서와 다름 | ✗ |
| **SJF** (참고) | 짧은 작업부터 | 세 작업 길이가 같아(206~207ms) 순서를 정할 근거가 없음 | 해당 없음 |
| **Priority (비선점)** | 우선순위 높은 작업부터 끝까지 실행, 등록 순서와 무관 | 등록 순서와 다른 B → C → A 순서, 각자 완료까지 독점 | ✓ |

**추론 근거 정리**

1. **비선점이다**: 한 작업이 시작되면 100% 완료될 때까지 다른 작업이 실행되지 않았다. 타임 퀀텀으로 번갈아 실행하는 Round-Robin이 아니다.
2. **도착 순서가 아니다**: 세 작업은 같은 시각(37.967)에 A, B, C 순서로 등록됐지만 B가 먼저, A가 마지막에 실행됐다. FCFS라면 A가 먼저여야 한다.
3. **길이 순서도 아니다**: 세 작업의 실행 시간이 같으므로 SJF로 B → C → A를 설명할 수 없다.
4. 따라서 등록 순서·길이와 무관한 **별도의 기준(우선순위)** 으로 다음 작업을 고르고, 고른 작업은 끝까지 실행하는 **비선점 Priority** 방식이 가장 잘 맞는다. 우선순위는 B > C > A로 보인다.

### 한계

- 900초 실행 동안 스케줄러 블록은 **부팅 직후 1회**만 찍혀 표본이 하나다. 여러 번 실행해서 순서가 매번 B → C → A로 같다면 고정 우선순위, 매번 다르다면 무작위 선택일 가능성도 있다. 추가 실행 로그로 확인할 예정이다.
- 이것은 **앱 내부 작업 스케줄러**의 동작이다. OS 수준 스케줄링(CFS)과는 별개이며, 앱이 프로세스 자체를 `nice=10`으로 낮춘 것은 OS 수준 우선순위 조정이다.

## 4. 결론 — 장단점과 적합한 서비스

**비선점 Priority 스케줄링**

| 장점 | 단점 |
|---|---|
| 중요한 작업을 먼저 처리해 핵심 작업의 완료 시간을 보장하기 쉬움 | 우선순위 낮은 작업은 계속 밀려 **기아(starvation)** 가 생길 수 있음 → 대기 시간에 따라 우선순위를 올려주는 **aging** 필요 |
| 비선점이라 작업 전환(문맥 교환)이 적어 오버헤드가 작고, 작업 중간 상태를 공유할 일이 적어 구현이 단순 | 긴 작업이 먼저 잡히면 그 동안 급한 작업이 와도 끼어들 수 없어 **응답 시간이 길어질 수 있음** |
| 작업 하나가 끝까지 실행되므로 캐시 지역성이 좋아 처리량에 유리 | 우선순위를 정하는 기준이 잘못되면 전체 성능이 나빠짐 |

**적합한 서비스**

- **배치·백오피스 처리 서버**에 적합하다. 예: 야간 정산에서 "결제 확정 > 리포트 생성 > 로그 정리" 순으로 중요도가 분명하고, 각 작업을 중간에 끊지 않고 끝내는 편이 처리량이 좋은 경우.
- **실시간 응답이 중요한 웹 서버에는 부적합**하다. 비선점이라 긴 작업이 실행 중이면 새로 들어온 사용자 요청이 기다려야 하므로, 이런 서비스는 작업을 시간 단위로 나눠 주는 Round-Robin이나 선점형 Priority가 낫다.
- 이 앱처럼 짧고 길이가 비슷한 내부 점검 작업 3개를 정해진 중요도대로 한 번에 처리하는 용도라면, 단순하고 오버헤드가 작은 비선점 Priority는 합리적인 선택이다.
